From Naive Loops to a Packed Microkernel: a CPU GEMM Worklog

GitHub · gemmx-cpp Paper (PDF) LinkedIn
November 2026

Pratham Srivastava

In this post, I iteratively optimize a single-threaded implementation of matrix multiplication (GEMM) in C++20 on my laptop CPU, an Intel Core i5-13450HX. The goal isn't to build a BLAS replacement. It's to measure, one idea at a time, how much each classic technique (loop order, cache blocking, SIMD, register blocking and packing) is actually worth on one real machine, instead of taking it on trust. Every step was run as an experiment: I wrote a prediction down before the run1, verified every kernel before timing it2, and kept the cases where I was wrong.

Matrix multiplication is the central kernel of dense linear algebra and of nearly all deep-learning training and inference. Its arithmetic is fixed at 2n³ floating-point operations, but its speed is not: the same arithmetic can run hundreds of times faster or slower depending on how it uses caches, SIMD units and registers. I start with the textbook triple loop and end at about 43% of the core's estimated peak3:

Yes, V3 is slower than V2. That's not a typo. It's the most useful result in the whole study, and it's why V4 looks the way it does.

Setup

All experiments ran on one laptop: an Intel Core i5-13450HX (Raptor Lake-HX, 6 performance cores plus 4 efficiency cores) with a 48 KiB 12-way L1d, a 1.25 MiB L2 and a 20 MiB shared L3, under Windows 11 + WSL25. Code is compiled with GCC 15.2 at -O3 in two builds: portable (baseline x86-64, so SSE2 only) and native (-march=native, so AVX2 and FMA). All kernels share one interface: row-major A, B and C, with C overwritten.

Throughput is reported as GFLOP/s = 2n³ / t. Every sample lasts at least 50 ms, every configuration is repeated five times and the median is reported. Every run writes its raw samples to CSV, together with the git commit, compiler and flags. Across the 316 configurations in the study, the median interquartile range was 1.6% of the median.

V0: Naive Implementation

The starting point is the triple loop straight out of a textbook. For each cell of C, walk along a row of A and down a column of B, and sum the products:

for (std::size_t i = 0; i < M; ++i) {
  for (std::size_t j = 0; j < N; ++j) {
    T sum = T{0};
    for (std::size_t k = 0; k < K; ++k) {
      // A(i, k) walks along a row: contiguous.
      // B(k, j) walks down a column: stride of N elements per step.
      sum += A(i, k) * B(k, j);
    }
    C(i, j) = sum;
  }
}

The problem is the inner loop's access to B. Matrices are stored row-major, so consecutive elements of a column of B are a whole row apart in memory. Every step of k lands on a new 64-byte cache line and uses 4 or 8 bytes of it. At n = 1024 in single precision, V0 runs at 0.53 GFLOP/s, about 0.2% of what the core can do.

The 4 KiB cliff

The naive kernel has a stranger problem too. Around n = 512 in double precision, throughput doesn't degrade smoothly. It falls off a cliff: 4.61 GFLOP/s at n = 511, then 0.92 at n = 512, a 5.0× collapse from adding one row and column. Single precision does the same thing at n = 1024 (4.17 → 0.79 GFLOP/s, 5.4×).

Both sizes have one thing in common: a row stride of exactly 4096 bytes. A cache line's set is fixed by its address. If a column's accesses are a stride of s cache lines apart, the column only touches 64 / gcd(s, 64) of the 64 L1 sets. At s = 64, every element of the column maps to the same set. A column of 512 values competes for 12 slots and keeps evicting itself, while the other 63 sets sit empty. The model predicts smaller dips too: n = 496 and 528 (s = 62 and 66, 32 sets each) are slower than 504 and 520 (s = 63 and 65, all 64 sets). That's what the data shows.

The prediction held. Hardware counters weren't available under WSL2, so I can't rule out TLB effects contributing as well6. Keep this cliff in mind, because packing in V4 is what finally removes it.

V1: Loop Order

The three loops can be nested in six orders. All six do identical arithmetic, so the only thing that changes is the memory access pattern. Here's ikj:

for (std::size_t i = 0; i < M; ++i) {
  T *crow = c + i * N;
  for (std::size_t k = 0; k < K; ++k) {
    const T aik = a[i * K + k];
    const T *brow = b + k * N;
    for (std::size_t j = 0; j < N; ++j) {
      crow[j] += aik * brow[j];
    }
  }
}

Now the inner loop takes one scalar of A and streams a whole row of B into a whole row of C. Both are contiguous, so every byte of every cache line gets used. And because there's no reduction anymore, the compiler is free to vectorize it.

The spread between orders is enormous, up to 85× at n = 1024:

As predicted, ikj and kij are fastest because they stream rows of B and C, and jki and kji are slowest because they walk columns of A and C. With -march=native, GCC vectorized ikj with AVX2 and sped it up 1.5–2.7×. ijk and jik didn't move at all, because their inner loop is a sum reduction7. The power-of-two cliffs only showed up in the column-walking orders.

One prediction failed. I expected ikj and kij to tie, but at n = 1024 ikj is clearly ahead (22.7 vs. 13.9 GFLOP/s). The reason: kij streams all of C once for every value of k, while ikj keeps one row of C in cache across the whole k loop.

V2: Cache Blocking

ikj is good while B fits in cache. Once it doesn't, every row of C drags the whole of B through the memory hierarchy again. Cache blocking fixes this by splitting the work into BS×BS tiles that are small enough to stay cached while they're reused. The tiles are visited in ii-kk-jj order, with ikj inside each tile:

for (std::size_t ii = 0; ii < M; ii += BS) {
  const std::size_t i_end = std::min(ii + BS, M);
  for (std::size_t kk = 0; kk < K; kk += BS) {
    const std::size_t k_end = std::min(kk + BS, K);
    for (std::size_t jj = 0; jj < N; jj += BS) {
      const std::size_t j_end = std::min(jj + BS, N);
      for (std::size_t i = ii; i < i_end; ++i) {
        T *crow = c + i * N;
        for (std::size_t k = kk; k < k_end; ++k) {
          const T aik = a[i * K + k];
          const T *brow = b + k * N;
          for (std::size_t j = jj; j < j_end; ++j)
            crow[j] += aik * brow[j];
        }
      }
    }
  }
}

Inside one tile step, the BS×BS tile of B is reused for every row of the tile, each a(i,k) is reused across BS columns, and each row segment of C stays hot across BS values of k.

I swept BS from 16 to 256. As predicted, there's an interior optimum at BS = 64–96. Very small tiles are slower than plain ikj because the inner loop is too short, and very large tiles stop fitting in cache.

The benefit grows with n. It peaks at 4.0× for double at n = 2000, where unblocked ikj collapses to 4.5 GFLOP/s once B no longer fits in L2. But the power-of-two sizes are still 27–32% slower than n = 2000, even with the best tile. Tile rows that are exactly 8 or 16 KiB apart still interfere in the cache. Blocking didn't fix the cliff.

V3: AVX2 Intrinsics, and Why They Didn't Help

The obvious next step is to stop trusting the compiler and write the SIMD by hand. V3 takes the BS = 64 blocked kernel and replaces only its innermost loop with AVX2/FMA intrinsics: broadcast a(i,k) into all 8 lanes, then load, FMA and store a vector of C:

const __m256 va = _mm256_set1_ps(aik);      // aik in all 8 lanes
for (; j + 8 <= j_end; j += 8) {
  __m256 vc = _mm256_loadu_ps(crow + j);
  const __m256 vb = _mm256_loadu_ps(brow + j);
  vc = _mm256_fmadd_ps(va, vb, vc);         // vc = va * vb + vc
  _mm256_storeu_ps(crow + j, vc);
}

Against the portable build, which is limited to 128-bit SSE2 without FMA, this is 1.5–2.0× faster, as predicted. But against the native build, GCC's own AVX2 code was equal or faster in nine of ten configurations: the V3/V2 ratio was 0.81–0.94 for float and 0.86–1.03 for double8. I had predicted a tie within 10%, so that held only partially.

The deeper reason is in the snippet above. Every single FMA comes with a load and a store of C. Faster instructions don't help when the bottleneck is how data moves, and both kernels move data the same way. To approach peak, C has to stay in registers and stop round-tripping through memory. That's V4.

V4: Packed Register-Blocked Microkernel

V4 follows the Goto/BLIS design. It changes two things at once. First, a small 6×16 tile of C is kept in registers across a long inner loop, the microkernel. Second, blocks of A and B are packed, i.e. copied into contiguous, zero-padded buffers laid out in exactly the order the microkernel reads them.

The microkernel

The 6×16 float tile of C is 6 rows × 2 AVX2 registers = 12 YMM accumulators. They're zeroed once, updated for all KC = 256 steps, and only then added into C:

for (std::size_t k = 0; k < kc; ++k) {
  const auto b0 = S::load(b);       // B[k, 0:8]
  const auto b1 = S::load(b + W);   // B[k, 8:16]
#pragma GCC unroll 6
  for (std::size_t r = 0; r < kMR; ++r) {
    const auto ar = S::bcast(a + r); // A[r, k] in every lane
    acc[r][0] = S::fma(ar, b0, acc[r][0]);
    acc[r][1] = S::fma(ar, b1, acc[r][1]);
  }
  a += kMR;     // next column of the A panel
  b += 2 * W;   // next row of the B panel
}

Each k-step issues two vector loads of B, six broadcasts of A and twelve independent FMAs. That's enough independent work to cover the FMA latency on the core's two FMA ports. C is read and written only once per KC-deep pass, instead of once per FMA as in V3.

The five loops

Around the microkernel sit five loops, each sized to one level of the memory hierarchy. I derived the sizes analytically from the cache parameters instead of autotuning them. One A micro-panel plus one B micro-panel should fit in about half of L1: (6 + 16) · 256 · 4 B ≈ 22.5 KiB for float. The packed A block (MC × KC = 288 × 256) targets L2, and the packed B block (KC × NC = 256 × 4096) targets L3.

for (jc = 0; jc < N; jc += NC)        // loop 5: NC = 4096
  for (pc = 0; pc < K; pc += KC) {     // loop 4: KC = 256
    pack_b(...);                       //   packed B block -> L3
    for (ic = 0; ic < M; ic += MC) {   // loop 3: MC = 288

Results

V4 is by far the biggest step of the ladder. In single precision it reaches 125 GFLOP/s at n = 1000 and 127 at n = 512, about 43% of the estimated peak, up from roughly 11% for the best V2/V3 kernels. Measured in the same run, it's 2.5–3.5× faster than the compiler-vectorized blocked kernel for float and 1.9–2.9× for double9.

The clearest effect is on the cliff. In the same run, the blocked kernel loses 23% at n = 1024 and 29–32% at n = 2048 relative to the neighbouring non-power-of-two size. The packed kernel loses at most 7.7%, and essentially nothing at n = 1024. Packed panels are contiguous buffers, so the 4 KiB row stride of the original matrices never reaches the inner loop.

Two things I didn't predict. First, the gain at n = 512 wasn't smaller than at larger sizes. Float is actually fastest there. Second, float stays flat near 125 GFLOP/s up to n = 1024, then drops to 106 and 98 at n = 2000 and 2048. Both drops coincide with the packed B block outgrowing the 1.25 MiB L2: about 1 MiB for float at n = 1024 versus 2 MiB at n = 2000. That suggests a smaller NC, one that keeps packed B in L2, would recover the large-n loss. I haven't tested that yet10.

What Mattered

Across the ladder, the steps that changed data movement mattered far more than the steps that changed instructions. Loop order, blocking and packing each changed which data gets reused and how contiguously it's read, and each one either produced a large gain or removed a cliff. Writing intrinsics without changing the data flow (V3) produced nothing over a good compiler. The same intrinsics combined with register blocking and packing (V4) produced the largest gain of all. The lesson I'm taking away: restructure the loops and the layouts first, and hand-vectorize only inside a register-blocked microkernel.

Writing predictions down before measuring made the misses as informative as the hits: kij losing to ikj, the compiler beating my intrinsics, and a 1.4× day-to-day drift in absolute throughput that I'd never have noticed otherwise.
